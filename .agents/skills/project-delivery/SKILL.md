# Project delivery

Treat repository project records as the shared source of truth.

## Existing-project flow

1. Read `AGENTS.md`, `PROJECT.md`, `DESIGN.md`, and all applicable `.project/` records before editing.
2. Complete only the first approved unblocked milestone.
3. Audit business usefulness, data rights, architecture, evaluation integrity, design, accessibility, performance, security, deployment, and public claims against verified evidence.
4. Build one complete stakeholder decision workflow without expanding the recorded authority boundary.
5. Update affected architecture, data, evaluation, evidence, state, handoff, publication, metric glossary, and data dictionary records when verified facts change.
6. Run `python3 scripts/project_kit.py check` before reporting milestone completion.

## Project-specific hard boundaries

- Use only the checksum-pinned UCI Default of Credit Card Clients source under CC BY 4.0.
- Exclude sex, education, marriage, and age from model inputs and public individual analytics; local aggregate fairness audit only.
- Describe scores and outcomes as retrospective academic research evidence, never as an approval, denial, price, recommendation, forecast, or production lending result.
- Keep credentials outside source and public artifacts.
- Do not deploy, publish, merge, change visibility, spend, roll back, or transmit repository content to Graphify without the exact approval recorded in `.project/approvals.yml`.

## Design and evidence gate

Apply `DESIGN.md`. Reject unsupported metrics, decorative charts, fabricated trends, vague business claims, and unexplained model jargon. Every metric must name its source, definition, denominator, interpretation, supported decision, and limitation. Screenshots require human visual approval before deployment.
